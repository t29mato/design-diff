# 実戦テスト: 実在の外部Pythonパッケージに対するdesign-diffの動作検証

**目的**: これまでの検証は自分自身(design-diff)とサンプルコードだけだった。公開後に
他人のコードで何が起きるかを、リリース前に手を動かして確認する。見るべきは
「正しい差分か」ではなく**「壊れずに完走するか」**(クラッシュ・無限ループ・
異常に長い実行時間・空の出力・巨大すぎる図)。

**方法**: pipでインストールできる実在のPythonパッケージ5つ+型注釈がほとんど無い
古いコードベース1つを対象に、実際にgit cloneし、各パッケージ自身の依存関係と
design-diffを同じ venv にインストールした上で(`design-diff`は対象コードを実際に
importするため、対象パッケージの依存が無いと即ImportErrorになる。実際のユーザーは
自分のプロジェクトの依存が揃った環境でdesign-diffを使うため、これが公平な検証方法)、
2つのタグ間で`design-diff diff`を実行した。

## 結果一覧(最終)

| パッケージ | バージョン範囲 | 完走可否 | 所要時間 | 気づいた点 |
|---|---|---|---|---|
| requests | v2.31.0 → v2.32.3 | ✅ 完走 | 0.90秒 | `HTTPAdapter.max_retries`属性が2行重複表示される**実バグを発見・修正**(型注釈のみの宣言と`__init__`代入の重複) |
| flask | 3.0.0 → 3.0.3 | ✅ 完走 | 0.89秒 | 当初`werkzeug.local.LocalProxy`の`repr()`評価で解析全体が失敗していたが、属性の型解決を自前実装に置き換えたことで解決(後述) |
| click | 8.1.0 → 8.1.7 | ✅ 完走 | 0.90秒 | 当初`import typing as t`というエイリアス付きimportが原因で失敗していたが解決 |
| rich | v13.6.0 → v13.7.1 | ✅ 完走 | 1.43秒 | 当初`TYPE_CHECKING`限定importによる前方参照解決の失敗があったが解決(型不明の属性として縮退表示) |
| httpx | 0.26.0 → 0.27.0 | ✅ 完走 | 0.99秒 | clickと同種の名前解決失敗があったが解決 |
| requests(旧) | v0.10.0 → v0.13.0(2012年頃、Python 2時代) | ❌ 解析失敗(クリーンに失敗) | 0.75秒 | Python 3では`cookielib`(Python 2専用モジュール)が無くimport自体が失敗。design-diffの対応範囲外(Python 3で実行できないコードは解析できない)。クラッシュではなく分かりやすいエラーで終了 |

**最終結果: 6件中5件が完走。唯一失敗したのは、Python 2専用構文を含み現在の
Python 3で実行不可能な、意図的に選んだ「型注釈もPython 3互換性も無い」古い
コードベースのみ**(design-diffの対応範囲外として妥当)。

## 経緯(3段階で発見・修正した問題)

### 第1段階: クラッシュ・無限ループは無いが、4/5パッケージが解析失敗

最初の実戦テストでは、flask/click/rich/httpxの4パッケージで解析が失敗した。
クラッシュ・無限ループ・異常な長時間実行は無く、全ケースが1.4秒以内に完走
または制御されたエラーで終了していた(これ自体は良い結果)。

### 第2段階: 真因の誤認と訂正

当初「`typing.X`形式の型注釈をpy2pumlが解決できない」と報告したが、**司令塔の
反証により不正確だったことが判明**(`import typing`をエイリアス無しで書けば
`typing.Dict[...]`は正しく解決される反例が提示された)。最小再現コードまで
絞り込んで検証し直した結果、真因は以下だった:

- **click/httpx**: `import typing as t`のような**importのエイリアス**。
  py2pumlの名前解決はモジュールの実際の名前空間に対する`getattr()`ベースで、
  エイリアス名ではなく正規名が束縛されていることを前提にしていた
- **rich**: 循環import回避のための**`TYPE_CHECKING`限定import**
  (`Optional["Live"]`という文字列前方参照が実行時に解決できない)
- **flask**: 上記2つとは別の、型解決のためのモジュール内総当たり走査中に
  無関係なオブジェクト(`werkzeug.local.LocalProxy`)の`str()`が失敗して
  クラッシュするバグ

詳細な最小再現コードは
[py2puml-resolution-failures-root-cause.md](./py2puml-resolution-failures-root-cause.md)
に記録した(歴史的記録として、当時「回避不能」と判断した根拠も含めて残してある)。

### 第3段階: 司令塔の実証実験により回避策が判明、実装して解決

司令塔が`typing.get_type_hints()`を使えば上記のケースがすべて正しく解決できる
ことを実機で証明した。design-diffは属性の型解決をpy2puml本体に任せるのを止め、
**抽出アダプタ内で`typing.get_type_hints()`を使って自前実装する**方向に変更した:

- **クラスの発見**(どのクラスが対象パッケージに属するか)は引き続き
  py2pumlの`filter_domain_definitions`を使う(安全で、クラッシュしない部分)
- **属性の型解決とそこから導かれる依存関係の抽出**は自前実装に置き換えた。
  `typing.get_type_hints()`はモジュールのglobalsに対して実際に注釈を評価する
  ため、エイリアスやTYPE_CHECKING限定importが絡んでいても正しく解決できる
- 1クラス・1属性ごとに例外を握りつぶし、解決できない場合はそのクラス/属性
  だけ縮退させる(型が不明のまま表示、または生の注釈文字列を返す)。
  解析全体を道連れにしない
- 副産物として、**この過程で別の実バグ(`flask/__main__.py`をimportすると
  FlaskのCLIが実際に起動してしまう問題)も発見・修正した**(後述)

結果、flask/click/rich/httpxすべてが完走するようになった。詳細な実装方針は
[py2puml-resolution-failures-root-cause.md](./py2puml-resolution-failures-root-cause.md)
の追記を参照。

## 修正した問題(最終)

1. **属性の重複表示バグ**: クラス本体で型だけ宣言し(`x: SomeType`。値の
   代入は無い)、`__init__`内で`self.x = ...`と代入する、よくあるPythonの
   イディオムに対し、同名の属性が重複して表示される回帰
   (`requests.adapters.HTTPAdapter.max_retries`で発見)
2. **解析失敗時の不親切なエラー**: 対象コードの解析が失敗する場合に、生の
   巨大なPythonトレースバックがそのままCLI/Actionの標準エラー出力に出ていた
   問題。分かりやすい説明を先頭に付けて非ゼロ終了するように修正した
3. **型注釈解決の根本的な作り直し**: py2puml本体のgetattr方式の型解決を、
   自前の`typing.get_type_hints()`ベースの実装に置き換えた
   (`own_attributes`)。エイリアス付きimport・TYPE_CHECKING限定importの
   両方を正しく解決できるようになった
4. **`__main__`モジュールの誤実行**: パッケージ内の全モジュールを走査する際、
   `<pkg>.__main__`をimportすると、ガードの無い`__main__.py`(例:
   `flask/__main__.py`は`from .cli import main; main()`のみでガード無し)が
   実際に実行され、design-diff自身のsys.argvをパースしようとして失敗する
   ことが判明。`__main__`モジュールを解析対象から除外するよう修正した

## 制約として残ったもの

- Python 3で実行できないコード(Python 2専用構文・モジュール)は解析できない
  (design-diff自体がPython 3.12+のみ対応のため、対応範囲外として妥当)
- 型アノテーションが無いコードでは依存(継承・コンポジション)が検出できない、
  という当初からの穏当な制約は変わらず有効
