# 実戦テスト: 実在の外部Pythonパッケージに対するdesign-diffの動作検証

**目的**: これまでの検証は自分自身(design-diff)とサンプルコードだけだった。公開後に
他人のコードで何が起きるかを、リリース前に手を動かして確認する。見るべきは
「正しい差分か」ではなく**「壊れずに完走するか」**(クラッシュ・無限ループ・
異常に長い実行時間・空の出力・巨大すぎる図)。

**方法**: pipでインストールできる実在のPythonパッケージ5つ+型注釈がほとんど無い
古いコードベース1つを対象に、実際にgit cloneし、**各パッケージ自身の実行時依存
関係とdesign-diffを同じvenvにインストールした上で**、2つのタグ間で
`design-diff diff`を実行した。

**重要な前提(HQ指摘・実戦テストの再検証で判明)**: design-diffは対象コードを
実際にimportして解析するため、**対象パッケージ自身の実行時依存関係が
design-diffの実行環境にインストールされている必要がある**(design-diff自身の
依存の問題ではない)。これはimportベースで解析する以上避けられない性質であり、
詳細は下記「制約として残ったもの」とREADMEのLimitationsに明記した。

## 結果一覧(最終)

| パッケージ | バージョン範囲 | 完走可否 | 所要時間 | classes_modified | relations |
|---|---|---|---|---|---|
| requests | v2.31.0 → v2.32.3 | ✅ 完走 | 1.23秒 | 1 | 0 |
| flask | 3.0.0 → 3.0.3 | ✅ 完走 | 1.08秒 | 22 | 3 added |
| click | 8.1.0 → 8.1.7 | ✅ 完走 | 0.95秒 | 23 | 4 added |
| rich | v13.6.0 → v13.7.1 | ✅ 完走 | 1.64秒 | 2 | 0 |
| httpx | 0.26.0 → 0.27.0 | ✅ 完走 | 0.98秒 | 28 | 1 removed |
| requests(旧) | v0.10.0 → v0.13.0(2012年頃、Python 2時代) | ❌ 解析失敗(クリーンに失敗) | 0.33秒 | - | - |

**最終結果: 6件中5件が完走**。唯一失敗したのは、Python 2専用構文を含み現在の
Python 3で実行不可能な、意図的に選んだ「型注釈もPython 3互換性も無い」古い
コードベースのみ(design-diffの対応範囲外として妥当)。**クラッシュ・無限
ループ・異常に長い実行時間・巨大すぎる図は1件も発生しなかった**。

## 経緯(4段階で発見・修正した問題)

### 第1段階: クラッシュ・無限ループは無いが、4/5パッケージが解析失敗

最初の実戦テストでは、flask/click/rich/httpxの4パッケージで解析が失敗した。
クラッシュ・無限ループ・異常な長時間実行は無く、全ケースが1.4秒以内に完走
または制御されたエラーで終了していた(これ自体は良い結果)。

### 第2段階: 真因の誤認と訂正

当初「`typing.X`形式の型注釈をpy2pumlが解決できない」と報告したが、**司令塔の
反証により不正確だったことが判明**(`import typing`をエイリアス無しで書けば
`typing.Dict[...]`は正しく解決される反例が提示された)。最小再現コードまで
絞り込んで検証し直した結果、真因は以下だった:

- **click/httpx**: `import typing as t`のような**importのエイリアス**
- **rich**: 循環import回避のための**`TYPE_CHECKING`限定import**
  (`Optional["Live"]`という文字列前方参照が実行時に解決できない)
- **flask**: 型解決のためのモジュール内総当たり走査中に無関係なオブジェクト
  (`werkzeug.local.LocalProxy`)の`str()`が失敗してクラッシュするバグ

詳細な最小再現コードは
[py2puml-resolution-failures-root-cause.md](./py2puml-resolution-failures-root-cause.md)
に記録した(歴史的記録として、当時「回避不能」と判断した根拠も含めて残してある)。

### 第3段階: 司令塔の実証実験により回避策が判明、実装

司令塔が`typing.get_type_hints()`を使えば上記のケースがすべて正しく解決できる
ことを実機で証明した。design-diffは属性の型解決をpy2puml本体に任せるのを止め、
**抽出アダプタ内で`typing.get_type_hints()`を使って自前実装する**方向に変更した
(詳細は`src/design_diff/adapters/extraction/_worker.py`のモジュールdocstring)。
副産物として、この過程で別の実バグ(`flask/__main__.py`をimportするとFlaskの
CLIが実際に起動してしまう問題)も発見・修正した。

### 第4段階: 依存関係のインストール漏れによる誤検出と、正式な再検証

置き換え直後の検証で、httpx/flaskが`ModuleNotFoundError`(idna/werkzeug)で
止まる事象が発生した。**これはdesign-diffの不具合ではなく、解析対象パッケージ
自身の実行時依存関係が検証環境にインストールされていなかっただけ**だった
(design-diffは対象コードを実際にimportして解析するため、対象パッケージの
依存も同じ環境に必要になる。importベースで解析する以上避けられない性質)。

各パッケージ自身の依存関係を正しくインストールした環境で6ケースを正式に
再実行した結果、**flask/click/rich/httpxすべてが完走**した(上記の結果表)。
この経験を踏まえ、ModuleNotFoundError/ImportErrorが発生した場合はCLI/Actionの
エラーメッセージで「対象パッケージ自身の依存をインストールしてください」と
案内するようにした(`Py2pumlExtractionError.friendly_message()`)。

## 修正した問題(最終)

1. **属性の重複表示バグ**: クラス本体で型だけ宣言し、`__init__`で実際の値を
   代入するイディオムで属性が重複表示される回帰
   (`requests.adapters.HTTPAdapter.max_retries`で発見)
2. **解析失敗時の不親切なエラー**: 生の巨大なトレースバックではなく、分かり
   やすい説明を出すようにした。ModuleNotFoundError/ImportErrorの場合は
   「対象パッケージ自身の依存をインストールしてください」という案内も追加
3. **型注釈解決の根本的な作り直し**: py2puml本体のgetattr方式の型解決を、
   自前の`typing.get_type_hints()`ベースの実装に置き換えた(`own_attributes`)
4. **`__main__`モジュールの誤実行**: `<pkg>.__main__`のimportで対象パッケージの
   CLIが実際に起動してしまう問題を修正(`__main__`モジュールを解析対象から除外)

## 制約として残ったもの

- **解析対象パッケージ自身の実行時依存関係が、design-diffの実行環境に
  インストールされている必要がある**(design-diff自身の依存の問題ではない。
  importベースで解析する以上避けられない性質)。GitHub ActionでPRに対して
  実行する文脈では、対象リポジトリ自身のCIで依存が既にインストールされた
  環境で動かすのが通常のため、実用上問題になることは少ない
- Python 3で実行できないコード(Python 2専用構文・モジュール)は解析できない
  (design-diff自体がPython 3.12+のみ対応のため)
- 型アノテーションが無いコードでは依存(継承・コンポジション)が検出できない、
  という当初からの穏当な制約は変わらず有効

## 第2弾: 母数を増やした追加の実戦テスト(2026-08-22)

**目的**: 前回とは異なる性質のパッケージ(科学計算・非同期・モダンなCLI・
古参のシステム系)を対象に加え、母数を増やすことで未知の失敗パターンを
見つける(HQ指示)。前回同様、各パッケージ自身の依存を正しくインストール
した上で実行した。

### 結果一覧

| パッケージ | バージョン範囲 | 性質 | 完走可否 | 所要時間 | 気づいた点 |
|---|---|---|---|---|---|
| numpy | v2.5.1 → v2.5.2 | 科学計算(C拡張・ビルドシステム有り) | ❌ 解析失敗(クリーンに失敗) | 2.17秒 | **新パターン**: ビルド時に生成される`numpy/version.py`が生のgitチェックアウトには存在せず、循環importで失敗(下記参照) |
| fastapi | 0.141.0 → 0.141.1 | Web(async, Pydanticベース) | ✅ 完走 | 3.72秒 | classes_modified: 2 |
| typer | 0.27.0 → 0.27.1 | モダンなCLI(型注釈を多用) | ✅ 完走 | 1.51秒 | classes_modified: 0(この2パッチ間では構造変化なし。正しい沈黙) |
| typer | 0.9.0 → 0.27.1(広い範囲) | 同上 | ❌ 解析失敗(クリーンに失敗) | 0.59秒 | **新パターン**: 広いバージョン範囲を跨ぐと、baseとheadで実行時依存関係の要件そのものが異なる場合がある(下記参照) |
| aiohttp | v3.14.2 → v3.14.3 | 非同期(async/await多用) | ✅ 完走 | 3.88秒 | classes_modified: 0 |

| paramiko | 4.0.0 → 5.0.0(メジャーバージョン跨ぎ) | 古参のシステム系(SSH) | ✅ 完走 | 2.20秒 | classes_added: 1, removed: 12, modified: 12, relations_added: 2, removed: 8。大きな差分でも完走 |

**総括: 7ケース中5ケースが完走。クラッシュ・無限ループ・異常な長時間実行
(全ケース4秒以内)は無し。** 失敗した2ケースはいずれも新しいパターンで、
以下で詳しく分析する。

### 新パターン1: ビルド時生成ファイルが生のgitチェックアウトに存在しない(numpy)

```
ImportError: cannot import name 'version' from partially initialized module
'numpy' (most likely due to a circular import)
```

numpyは`numpy/version.py`(または類似のバージョン情報モジュール)をビルド
システム(meson)がビルド時に生成しており、これは**gitで管理されたソース
ツリーには含まれない**。design-diffは`git worktree add`で対象refを生の
ソースツリーとして展開し、それを直接importするため、ビルド生成物が必要な
パッケージは、pipで正しくインストールされた実体(ビルド済み)とは異なり、
そのままではimportできない。

**回避可能性の検討(HQ指示: まず標準ライブラリの代替を疑う)**: これは型注釈
解決の問題ではなく、**そもそも対象コードがimport可能な状態にない**という、
より手前の段階での失敗であり、`typing.get_type_hints()`のような型解決の
工夫では対応できない。原理的な回避策は「`git worktree add`で生の
ソースツリーを展開する」のではなく「実際にpipでビルド・インストールした上で
importする」という、抽出の前提そのものを変える大きなアーキテクチャ変更に
なる。これは影響範囲が大きく(ビルドシステムの多様性・ビルド時間の増大等)、
今回は**修正せず、既知の制約として記録するに留める**。

### 新パターン2: 広いバージョン範囲では、base/headで必要な依存関係自体が異なりうる(typer)

```
ModuleNotFoundError: No module named 'click'
```

typerの最新版(0.27.1)は`click`への直接依存を持たない(pyproject.tomlの
`dependencies`に`click`が無いことを確認済み)が、古い版(0.9.0)のコードは
`from click.exceptions import Abort as Abort`のように実際に`click`を
importしている。`pip install typer==0.27.1`で構築した環境には
(最新版の依存関係一覧に基づき)`click`がインストールされておらず、
`git worktree add`で展開した0.9.0側のコードがimportできずに失敗した。

これは前回ドキュメント化した「対象パッケージ自身の依存関係が必要」という
制約の、**新たに判明した重要な補足**: 対象パッケージ自身の依存関係は
**バージョンによって変わりうる**ため、1つの環境にインストールした依存関係
(通常はhead側のバージョンの要件)だけでは、base側のバージョンを解析するには
不十分な場合がある。

**回避可能性の検討**: これも型注釈解決とは無関係な、依存関係インストールの
問題であり、標準ライブラリでの代替は成立しない。原理的な回避策(baseとhead
それぞれに対応する依存関係を別々にインストールする)は、design-diffが対象
パッケージのバージョンごとの依存関係を解決してインストールする責務を新たに
負うことを意味し、大きなスコープ拡大になる。**今回は修正せず、既知の制約
として記録するに留める。** 実用上は、baseとheadが近いバージョン(依存関係が
大きく変わっていない範囲)であれば問題にならない(実際、同じtyperで隣接する
パッチバージョン同士の比較は問題なく完走した)。

### 更新した制約一覧(README Limitationsにも反映)

- **対象コードがビルド時にファイルを生成するパッケージ(numpy等)は解析できない
  場合がある**。design-diffは`git worktree add`による生のソースチェックアウトを
  直接importするため、ビルドシステムが生成するファイルに依存するコードは
  importに失敗しうる
- **広いバージョン範囲を比較する場合、base側とhead側で対象パッケージ自身の
  依存関係の要件が異なることがある**。1つの環境に依存関係をインストール
  しただけでは、両方のバージョンを解析するのに不十分な場合がある(近い
  バージョン同士の比較では通常問題にならない)
